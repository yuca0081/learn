Go for Java Engineers · Lesson 05

goroutine 与 channel：换一种方式写并发

预计 35 分钟 · 前置：第 4 课 接口与组合 · 学完你能：用 goroutine / channel / WaitGroup / select 写出地道的 Go 并发，把一段 Java 线程池代码翻译成 Go

本课目标：Java 的并发围绕线程池、锁和 Future；Go 的并发围绕goroutine 和 channel——线程便宜到不用池，数据靠管道传递而不是靠锁保护。这是 Go 最强的一面，也是它最初走红的原因。读完请完成 翻译练习 和 检索测验。

1 · goroutine：go 一个关键字

Java 里跑并发任务，你先想线程池：Executors.newFixedThreadPool(n)——因为 OS 线程贵（约 1MB 栈、内核调度），开几千个系统就吃力。Go 把这件事直接拆掉了：

Java
ExecutorService pool =
    Executors.newFixedThreadPool(4);
pool.submit(() -> {
    System.out.println("干活");
    return null;
});
// 用完还得 shutdown()
Go
go func() {
    fmt.Println("干活")
}()
// 就这样。没有池，没有 shutdown

go f() 让函数在新的 goroutine 里运行，语句本身立即返回、绝不等待。goroutine 是用户态调度的轻量执行体：起步约 2KB 栈、按需增长，单机开几十万个是常态——所以 Go 社区基本不用"池"，要并发就 go 一个。

func main() {
	go say("world")   // 新 goroutine，立即返回
	say("hello")      // main 自己继续跑
	time.Sleep(time.Second)  // 演示专用：真代码不靠 Sleep 等待
}
新手第一坑：main 函数一退出，所有 goroutine 直接被杀，没有任何 join 或优雅关闭。如果你的 goroutine "没输出"，八成是 main 跑完了。所以真实代码永远要有等待机制——下一节的 WaitGroup 或 channel。

官方教程：A Tour of Go · goroutine。

2 · 等它们跑完：sync.WaitGroup

等一组 goroutine 全部完成，标准工具是 sync.WaitGroup——角色相当于 Java 的 CountDownLatch（或挨个 join()）：

var wg sync.WaitGroup
for i := 0; i < 3; i++ {
	wg.Add(1)             // 计数 +1，必须放在 go 之前
	go func(id int) {
		defer wg.Done()   // 计数 -1，defer 保证任何出口都执行
		fmt.Println("worker", id, "完成")
	}(i)
}
wg.Wait()                 // ≈ latch.await()：计数归零才继续
fmt.Println("全部完成")

三条纪律：Add 放在 go 语句之前（放 goroutine 里，Wait 可能提前通过）；Done 用 defer（panic 也不会漏减，第 3 课的 defer 在这里闪光）；goroutine 之间不共享局部变量，要传就传参。

Go 1.22 起 for 循环变量每次迭代都是新变量，闭包可以直接捕获 i；旧版本会三个 goroutine 共享同一个 i——所以老代码里常见 go func(id int){...}(i) 传参写法，看到别奇怪。

3 · channel：类型化的管道

goroutine 各跑各的，数据怎么来往？Java 的答案是共享对象 + 锁；Go 的答案是 channel——一根类型化的管道，语言级语法（不是类库）：

ch := make(chan string)   // 无缓冲 channel

ch <- "hi"                // 发送：阻塞到有人接收
msg := <-ch               // 接收：阻塞到有人发送
fmt.Println(msg)
  • 无缓冲 channel 是"握手"：发送方阻塞到有接收方到场、两边交接完才各自继续——和 Java 的 SynchronousQueue 同语义。它天然是两个 goroutine 之间的同步点。
  • 类型严格：chan int 只能传 int，编译器检查，没有 Object 装箱那套。
  • 方向可以声明在类型上：func worker(jobs <-chan string, results chan<- int)——只收 jobs、只发 results，写反了编译报错。看函数签名就知道数据流向。

官方教程：A Tour of Go · channel。

4 · 缓冲、关闭与 range：channel 的生命周期

ch := make(chan int, 3)   // 容量 3 ≈ new ArrayBlockingQueue<Integer>(3)
ch <- 1                   // 没满，不阻塞
close(ch)                 // 发送方宣布：不会再发了

v, ok := <-ch             // 排空期间 ok=true；排空后 v=0, ok=false
for x := range ch {       // 收到关闭信号自动退出循环
	fmt.Println(x)
}

close(ch) 是发送方的"我说完了"信号，接收方靠 ok 或 range 感知结束——Java 里你得发明"毒丸对象"塞进队列让消费者停工，Go 把它做成了语言特性。

channel 行为铁律：① 只由发送方关闭，且只关一次——向已关闭的 channel 发送是 panic，重复 close 也是 panic；② 从已关闭的 channel 接收不 panic：先排空，然后永远立即返回零值 + false，绝不阻塞；③ nil channel（零值）收发都永久阻塞——"忘了 make"的症状就是整个程序卡死。记不全就记这张小表：
操作nil channel已关闭正常
发送 ch <-永久阻塞panic阻塞到有接收者 / 有空位
接收 <-ch永久阻塞零值 + false（不阻塞）阻塞到有发送者 / 有数据
close(ch)panicpanic—

5 · select：同时等多个 channel

一个 goroutine 要等好几路消息（数据、超时、退出信号），Java 里得 CompletableFuture.anyOf 或自己组合条件锁；Go 里是语言级的 select：

select {
case msg := <-ch1:
	fmt.Println("收到:", msg)
case ch2 <- "x":
	fmt.Println("发出去了")
case <-time.After(time.Second):
	fmt.Println("等超时了")   // time.After 返回一个定时 channel
}
  • 多个 case 同时就绪 → 随机选一个（防止某一路被饿死）；全没就绪 → 阻塞。
  • 加 default: 分支就变成非阻塞探测——"有就处理，没有先干别的"。
  • case 是 channel 操作，发送和接收都能等。

官方教程：A Tour of Go · select；Go by Example：Select。

6 · 哲学：通过通信共享内存

Go 也有锁：sync.Mutex（≈ ReentrantLock）、sync.Once、sync/atomic，都能用。但社区的信条是 Rob Pike 那句话：

Don't communicate by sharing memory; share memory by communicating.
不要用共享内存来通信，要用通信来共享内存。

落到写法上：数据的所有权随 channel 转移——一个 goroutine 把数据发出去，就别再碰它；接收方拿到后独占处理。没有两个执行流抢同一块内存，多数场景锁就不需要了。拿不准有没有竞争时，让编译工具替你查：

go run -race main.go     # 或 go test -race
# 内置数据竞争检测器：发现无同步的并发读写直接报

实战分工：goroutine 之间传数据、传结果、传"做完了" → channel；保护结构体内部的字段（如缓存的 map） → sync.Mutex。锁是最后手段，不是默认选项。

官方博客：Share Memory By Communicating（中文版）；《Go 语言圣经》第 8 章 goroutine 和 channel。

7 · 动手练习：把 Java 翻译成 Go

任务：把下面的 Java 翻译成 Go。模式是并发课最常见的"扇出—收集"：每个任务一个 goroutine（≈ submit），结果从 channel 收（≈ Future.get），WaitGroup 等全部完成：

待翻译的 Java
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public class Main {
    public static void main(String[] args) throws Exception {
        List<String> urls = List.of("go.dev", "java.com", "golang.org");

        ExecutorService pool = Executors.newFixedThreadPool(3);
        List<Future<Integer>> futures = new ArrayList<>();
        for (String u : urls) {
            futures.add(pool.submit(u::length));   // 每个任务一个 Future
        }

        int sum = 0;
        for (Future<Integer> f : futures) {
            sum += f.get();                        // 阻塞等每个结果
        }
        pool.shutdown();
        System.out.println(sum);  // 6+8+10 = 24
    }
}

先自己写，贴进 Go Playground 验证输出是 24，再对照答案：

查看参考答案（先自己写！） 
package main

import (
	"fmt"
	"sync"
)

func main() {
	urls := []string{"go.dev", "java.com", "golang.org"}
	results := make(chan int)

	var wg sync.WaitGroup
	for _, u := range urls {
		wg.Add(1)                 // 放在 go 之前
		go func(url string) {     // ≈ pool.submit
			defer wg.Done()
			results <- len(url)   // ≈ Future 里塞结果
		}(u)
	}

	go func() {
		wg.Wait()                 // 全部完成后……
		close(results)            // ……由这个 goroutine 关闭结果管道
	}()

	sum := 0
	for n := range results {      // ≈ 逐个 f.get()，收完自动退出
		sum += n
	}
	fmt.Println(sum)              // 24（结果顺序无关，总和确定）
}

自评清单：① wg.Add(1) 在 go 语句之前？② goroutine 里用 defer wg.Done()？③ 发送全在 goroutine 里、main 只负责收？④ close(results) 在 wg.Wait() 之后的独立 goroutine 里（main 还在 range 阻塞收数，不能自己关自己收）？⑤ 收结果用 range 自动退出？——五条全中，你就把 Go 并发的黄金骨架写出来了。这个"扇出 + WaitGroup + close + range 收尾"的模式值得背下来，生产代码里到处都是它。

9 · 闭卷回忆

最后 60 秒，不看上文回答三个问题，再滚动到底部核对：

  1. main 函数退出时，其他 goroutine 会怎样？用什么等待它们？
  2. 无缓冲和有缓冲 channel 的阻塞规则分别是什么？向已关闭的 channel 发送和接收各会发生什么？
  3. channel 应该由谁关闭？for range ch 什么时候结束？
核对答案
  1. 直接被杀，没有优雅关闭；用 sync.WaitGroup 或 channel 等待。
  2. 无缓冲：发送等接收者、接收等发送者（握手）；有缓冲：满了发送才阻塞、空了接收才阻塞。发送到已关闭 → panic；接收 → 不 panic，排空后立即得零值 + ok=false。
  3. 发送方（且只关一次）；接收方排空所有已发送的值后自动退出。
